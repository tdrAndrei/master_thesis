\section{\label{sec:introduction}Introduction}
Expressive type systems let programmers state invariants in the types of their programs, so that errors are reported at compile time instead of at run time.
Dependent type systems represent a significant step in this direction. They extend conventional type systems by allowing types to depend on values. This added expressiveness enables the encoding of precise specifications. This includes, for instance, types that capture the exact length of a list or enforce domain-specific constraints. As shown by the Curry-Howard correspondence \autocite{reis_curry-howard_nodate}, such type systems can express logical proofs. Writing a well-typed program becomes equivalent to constructing a proof of a logical proposition. As a result, languages with dependent types can function as proof assistants for higher-order intuitionistic logic. Implementations of these ideas can be seen in systems such as Lean, Agda, and Idris~2, where programming and formal verification are tightly integrated. The dependent type calculus introduces $\Pi$-types of the form $(x:A) \rightarrow B$, where $x$ can appear in the definition of $B$, apart from the regular function type $A \rightarrow B$. The variable $x$ is only known when we apply the function to an argument. The actual value of the argument will then be substituted for $x$ in $B$, to obtain the return type. 

For a dependently typed language to be considered practical, it needs to perform as much type inference as possible to avoid requiring
programmers to provide information that can be reconstructed from context.
Consider the function that adds an element to the head of a length-indexed
vector:
\[
    \mathit{cons} :
    (A : \mathit{Set}) \rightarrow
    (n : \mathit{Nat}) \rightarrow
    A \rightarrow
    \mathit{Vec}\ A\ n \rightarrow
    \mathit{Vec}\ A\ (\mathit{suc}\ n).
\]

The arguments $A$ and $n$ describe the element type and length of the input
vector. Requiring both arguments at every application would be cumbersome, so
dependently typed languages commonly allow them to be omitted when they can be
recovered from the remaining arguments. Recovering such arguments requires the type checker to compare dependent
types. For example, if the final argument has type $\mathit{Vec}\ A\ n$, then
the omitted length argument must be chosen so that the expected input type of
$\mathit{cons}$ agrees with that type. In general, the inferred term may depend on variables introduced by surrounding binders. Solving an equality between types can require inferring not only a term, but a function of the variables currently in scope, which is more complex than first-order unification and motivates the use of higher-order unification \autocite{mazzoli2016typechecking,miller_logic_1991}.

Binding introduced by dependent function types is, however, only one aspect of
name binding in a programming language. Name resolution may also depend on
modules, imports, inheritance, qualified names, and forward references. These
visibility relations do not necessarily follow the lexical nesting of the
abstract syntax tree
\autocite{4bf44aa1779c4a968c555e1b54e16119,neron_extensible_2015}. A language
implementation for dependent types has to support both the binding
structure that arises inside terms and types and the broader name-resolution
mechanisms of the surrounding programming language.

Language workbenches \autocite{erdweg_evaluating_2015} reduce the cost of implementing such a language. They provide reusable, declaratively specified infrastructure for parsing, name binding, type checking, and editor support. This is interesting for dependently typed languages, whose type checkers combine higher-order unification, weak head normalisation, and careful handling of binding and scope, all of which are cumbersome to build from scratch.

Spoofax \cite{6898704} is a language workbench developed at TU Delft.
Static semantics in Spoofax can be specified using Statix \cite{van_antwerpen_scopes_2018},
a constraint-based language for expressing typing and name-resolution rules.
Statix represents name binding explicitly through scope graphs. Scope graphs
model scopes as nodes and visibility relations as labelled edges, allowing
lexical and non-lexical name-resolution mechanisms to be expressed within the
same framework \cite{van_antwerpen_scopes_2018}. This makes them particularly suitable for
features such as imports, qualified references, and forward references.

However, the term language and built-in unification mechanism of Statix are
first-order. Binding structure is represented externally through the scope
graph rather than through binders in the meta-language. As a result,
operations needed by dependent type checking, such as substitution under
binders and higher-order unification of metavariables, cannot simply be
delegated to the host language and must instead be expressed explicitly.

A different approach is Higher-Order Abstract Syntax (HOAS)
\cite{pfenning_higher-order_nodate}, where object language binders are represented using
binders of the meta-language. In higher-order logic programming systems, this
representation provides direct support for operations such as capture-avoiding
substitution and higher-order unification. The trade-off is that such binding
mechanisms are fundamentally lexical, whereas scope graphs are designed to
represent more general visibility relations between scopes.

This trade-off motivates the central question of this work: can higher-order pattern unification be integrated with a scope-graph-based constraint system (RQ1)? Furthermore, how does such an approach compare to higher-order logic programming systems when implementing a dependently typed language (RQ2)?

To address these questions, we design and implement a higher-order pattern unification algorithm inside a scope-graph framework, and analyse its implications for implementing dependently typed languages in Spoofax.

\subsection{\label{sec:contributions}Contributions}

This paper addresses two research questions and makes the following contributions.

\paragraph{Higher-order pattern unification in scope-graph systems.}
We implement and study an algorithm for higher-order pattern unification in a constraint-based system that uses scope graphs for name binding. To validate the algorithm, we implement a minimal dependently typed core language in Statix (\cref{sec:Language,sec:Inference}), demonstrating that higher-order pattern unification can be integrated with scope-graph-based name resolution and supports core dependent type features.

\paragraph{Comparison of implementation paradigms for dependent typing.}
We provide a structured comparison between higher-order logic programming systems such as $\lambda$Prolog and scope-graph-based constraint systems in \cref{sec:ScopeGraphs}. The analysis qualitatively compares implementation trade-offs, including the treatment of binding, fresh name generation, modularity, and non-lexical scoping.

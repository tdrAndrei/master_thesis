\section{\label{sec:statix}Background}

This section introduces dependent types and the name-binding requirements they
impose, and then the two approaches to name binding compared in this paper:
scope graphs and higher-order abstract syntax.

\subsection{Dependent Types}
In most conventional type systems, the set of invariants a compiler can check is
fixed by its implementation. Dependent type systems, as introduced by
Martin-L{\"o}f \autocite{martinlof1984intuitionistic}, let types depend on
values, so programmers can express and verify their own invariants within the
type system. Binding values in types in turn requires type-level computation
(reduction). We use Agda \autocite{norell2007practical} for examples.

\subsubsection{Function types and Pi types}
In the simply typed lambda calculus, a function type $A \to B$ describes functions that
take an argument of type $A$ and return a result of type $B$. The return type
$B$ is fixed and cannot refer to the value of the argument. A \emph{dependent
  function type} (or \emph{Pi type}), written $(x : A) \rightarrow B \ x$, generalises this by letting the return type $B \ x$ mention the argument $x$. When the return type does not depend on the argument, the Pi type reduces to an ordinary function type $A \to B$. As a first example, consider a function \texttt{zeros} : $\,(x : \mathsf{Int}) \rightarrow \, \mathsf{Vec} \  \mathsf{Int} \ x$, which produces a vector of zeros with length $x$. This cannot be expressed at the type level with an ordinary function type in the simply typed lambda calculus. 

In practice, many type arguments can be inferred from context. Most dependently typed languages allow such arguments to be marked as \emph{implicit}, meaning they are automatically filled in by the type checker. The canonical example is the identity function, which can be given the type $\text{id} : \{A : \text{Type}\} \to A \to A$, where the braces indicate that $A$ is implicit. The caller writes $\text{id}\; 42$ rather than
$\text{id}\; \mathbb{N}\; 42$, and the type checker infers that $A = \mathbb{N}$. This ability to infer implicit arguments is in fact a central motivation for this work. 

\subsection{Name binding}
Static analysis typically infers information about a name where it is
\emph{declared} and reuses it at its \emph{references}. Mapping each reference
to its declaration is called \emph{name resolution}
\autocite{4bf44aa1779c4a968c555e1b54e16119}. The rules for name resolution are
set by the language's scoping discipline. Under \emph{lexical scoping}, the most
common one \autocite{scott_programming_2015}, resolution proceeds outward
through the enclosing scopes of the AST and inner declarations shadow outer
ones. Many practical languages also have \emph{non-lexical} scoping that the AST
hierarchy cannot explain, such as module imports, class inheritance, qualified
names, and forward references. A type checker can then no longer simply follow
the AST: to check forward references, for instance, it must collect all
declarations of a scope before checking their uses. In most languages such
scoping is handled in an ad-hoc manner inside the type checker
\autocite{neron_extensible_2015}.

\subsection{Name binding in dependent types}

A dependently typed language adds subtle complexities to the name binding and resolution process. One difference from a simply typed language is the ability to bind variables (of any type) in types. When defining a function $f$ with argument $x$, the variable $x$ is bound both in the body of $f$ and in its return type. Another challenge of name binding comes with inference. In dependently typed languages inference is complex and requires higher-order unification \autocite{mazzoli2016typechecking,demoura2015elaboration,abel_extensions_2018}. This complexity arises from the presence of binders at the type level. In particular, when unifying two types, the solution can depend on these binders and will generally have the form of a function. More details about this process and how it is integrated into type checking are given in \cref{sec:hou}. 

Inference is commonly implemented by inserting \emph{metavariables} where a term
must be inferred. Unlike ordinary bound variables, metavariables start out
unsolved. Later, unification constraints generated during elaboration progressively
assign them \emph{solutions} until the missing information is reconstructed
\autocite{gundry2010typeinference,dunfield2013complete}. In contrast to
Hindley-Milner inference \autocite{milner1978theory,damas1982principal}, where
first-order unification suffices, these solutions may depend on binders.
Because a metavariable may be solved in a different scope from the one in
which it was created, metavariables also pose a scoping problem of their own,
which we return to in \cref{sec:scopingmetas}.


\subsection{Scope Graphs}

Modern programming languages combine multiple scoping mechanisms, including lexical scoping induced by syntactic structure and non-lexical scoping arising from constructs such as imports, inheritance, or other visibility relations. Traditional formulations of name resolution, for instance based on hierarchical symbol tables, are well-suited for purely lexical scoping but become increasingly ad hoc when extended to accommodate such non-lexical mechanisms. Scope graphs provide a uniform representation in which both forms of scoping are modelled within a single formalism, by representing scopes as nodes in a graph and scoping relations as labelled edges.

Formally, a scope graph is a directed labelled graph $G = (S, E, D)$, where $S$ is a set of scopes, $D$ is a set of declarations, and $E \subseteq S \times L \times S$ is a set of labelled edges between scopes, for some set of labels $L$. Each declaration $d \in D$ is associated with a scope in $S$ and introduces a name. References to names occur in scopes and must be resolved to declarations. Lexical scoping is typically represented by edges corresponding to syntactic nesting, whereas non-lexical scoping mechanisms, such as imports or inheritance, are represented in the same graph as additional labelled edges \autocite{van_antwerpen_scopes_2018}. This representation abstracts from the concrete language constructs and instead captures name binding in terms of reachability in the graph.

Name resolution is defined as a path search problem over the scope graph. Given a reference to a name $x$ in a scope $s \in S$, resolution is equivalent to finding a declaration $d$ of $x$ in some scope $s'$ such that there exists a path from $s$ to $s'$ that satisfies a given resolution policy. Such a policy constrains the admissible sequences of edge labels and typically induces a preference ordering over paths in order to model shadowing. In particular, declarations that are reachable via preferred paths (for example, shorter paths or paths following specific edge labels) take precedence over others, ensuring that more local declarations shadow those that are more distant in the graph.

\subsection{Statix}

The ideas brought by scope graphs have been implemented in Statix, which is a constraint-based language used in the Spoofax language workbench for
specifying type systems and name resolution declaratively. Rather than constructing the scope graph procedurally, one specifies constraints that introduce scopes, declarations, and edges, as well as constraints that require certain references to resolve to declarations. Concretely, scope construction is expressed using constraints that generate fresh scopes, introduce declarations of names in scopes, and relate scopes via labelled edges. Name resolution is expressed by constraints of the form $\texttt{resolve}(s, x) = d$, requiring that the reference to $x$ in scope $s$ resolves to declaration $d$ according to the resolution policy induced by the scope graph.

The principal design choice in Statix is that terms are first-order: they are constructed from user-defined constructors and variables, but do not include higher-order constructs such as lambda abstractions. As a result, binding structure is not represented within terms themselves, but externally via scope graphs. Likewise, unification in Statix is restricted to first-order terms.
This separation enables flexible modelling of complex scoping mechanisms, including non-lexical scoping. 

An advantage of Statix is that scope graph constraints interact with other
semantic constraints, such as typing constraints: resolving a reference yields a
declaration whose type may be subject to further constraints, so name
resolution is part of a single constraint system rather than a separate phase.
Resolution constraints are solved only once the relevant part of the scope graph
is closed, that is, once Statix knows that the scope will not be extended.
Otherwise, they are suspended until more scopes, edges, and declarations are
added. This is what allows a type checker to handle forward references since a
reference can be required to resolve before its declaration has been created.

\subsection{Higher-Order Abstract Syntax}

An alternative approach to modelling name binding is given by Higher-Order
Abstract Syntax (HOAS), in which binding constructs of an object language are
represented using the binding mechanisms of a meta-language. A bound variable is
represented by a meta-level variable, so substitution and $\alpha$-equivalence
are handled implicitly by the meta-language. For example, a
$\lambda$-abstraction is represented as a meta-level function wrapped in a
\texttt{Lam} constructor:
\begin{align*}
[\![\lambda x.\ body]\!] \Rightarrow \mathsf{Lam}(\mathsf{fun}\ x \Rightarrow body)
\end{align*}

In functional meta-languages such as Agda or Coq, HOAS is hampered by the
intensional function space, which does not allow functions to be inspected, and
by strict positivity, which rejects constructors such as
\texttt{Lam : (Term $\rightarrow$ Term) $\rightarrow$ Term}. Parametric HOAS
\autocite{PHOAS} mitigates these problems at the cost of a more indirect
representation. Logic programming languages are a more natural fit.
$\lambda$Prolog and its descendants use $\lambda$-tree syntax
\autocite{lambda-tree}, in which programs define and quantify over lambda terms
and the runtime manages fresh variables as eigenvariables. In our work we use Elpi
\autocite{dunchev_elpi_2015}, an embeddable $\lambda$Prolog implementation
whose unification is restricted to the decidable higher-order pattern fragment.
Typing rules become clauses in which the meta-language introduces fresh
variables and extends the typing context (\cref{sec:ScopeGraphs}).

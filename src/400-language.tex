\section{\label{sec:Language}A Language with Dependent Types in Statix}

This section presents the dependently typed language that we implement in
Statix.

\subsection{Language}
The language implemented in Statix showcases the powerful features of dependent types. The core of the language is a lambda calculus with Pi types and let bindings. Concretely, the syntax of our language is defined in SDF3:
\begin{lstlisting}[caption={Necessary syntax for dependent types}, language=SDF3]
Expr.Let = [let [ID] = [Expr]; [Expr]]
Expr.Set = "Set"
Expr.Var = ID
Expr.Pi = "(" ID ":" Expr ")" "->" Expr {right}
Expr.Lam = "\\" ID "." Expr
Expr.App = Expr Expr {left}  
Expr.Ann = Expr "::" Expr
\end{lstlisting}

\noindent The language is formed from lambda abstractions, applications, variables, let bindings, Pi types and type annotations. The latter are very important for our bidirectional type checking approach \autocite{dunfield2022bidirectional}. In this method a type checker has two routines: infer and check. Variables, let expressions and applications are inferable, while lambda abstractions need to be checked against a type. Type annotations mark the transition from infer mode to check mode. Lastly, the \texttt{Set} constructor represents the type of types. In our language, \texttt{Set} has type \texttt{Set}. This allows Girard's paradox \autocite{hurkens1995simplification}, which shows that self-referential universes can derive a contradiction. However, the typing of \texttt{Set} is implemented in the language without loss of generality and can easily be extended with universe levels like in Agda. \par
The two routines required for bidirectional typing have the following signatures:
\begin{lstlisting}[language=Statix]
infer : scope * Expr -> (Expr * Expr)
check :  scope * Expr * Expr -> Expr
\end{lstlisting}
Both infer and check take the current scope and an expression from the object language. \texttt{check} also takes a type as an additional argument. Normally, infer would return the inferred type, while check would not return anything since it would either succeed or fail. The extra \texttt{Expr} comes from the fact that both relations refine their input terms, meaning variables get replaced with fresh variables with globally unique names. In \cref{sec:Inference} we will also show how placeholders \texttt{\_} are refined to metavariables. Lastly, the following example represents a valid program in our language:
\begin{lstlisting}
(\T.\x. x) :: (T : Set) -> (t : T) -> T
\end{lstlisting}
We are given an annotated lambda term \texttt{\textbackslash T.\textbackslash x.x} which we can check against \texttt{(T : Set) → (t : T) → T}. The example will type check since we know that T is a type, x has type T and the return types match.

\subsection{Typing rules} In the following we formalise the type checking rules for the language. Since we are working within a bidirectional framework, we use the notation $e \Uparrow T \leadsto e'$ to express that term $e$ is inferred to type $T$ and can be refined to term $e'$. Furthermore, $e \Downarrow T \leadsto e'$ is read similarly, but term $e$ is checked against a given type $T$. We also require a symbol to express equality between two terms: $x \equiv y$.

\begin{mathpar}
  \textbf{Inferred terms} \\
  \inferrule*[Right=Let]{
    s \vdash a \Uparrow A \leadsto a' \quad (x_{fresh}, A)::s \vdash b \Uparrow T \leadsto b'
  }{s \vdash (\mathsf{let}\ x = a;\ b) \Uparrow T \leadsto (\mathsf{let}\ x_{fresh} = a';\ b')}

  \inferrule*[Right=Var]
  {s \vdash \mathsf{getTy}(s, v) = T \quad s \vdash \mathsf{declaredID}(s, v) = v'}
  {s \vdash Var(v) \Uparrow T \leadsto Var(v')}

  \inferrule*[Right=Set]
  {s\vdash}{s \vdash Set \Uparrow Set \leadsto Set}

  \inferrule*[Right=App]
  {s\vdash f \Uparrow (x : A) \rightarrow B \leadsto f' \quad s \vdash e \Uparrow A' \leadsto e' \quad A' \equiv A \quad [x\mapsto e']s \vdash B \Rightarrow_{\beta} R}
  {s \vdash f\ e \Uparrow R \leadsto f'\ e'}

  \inferrule*[Right=Ann]
  {s\vdash T \Downarrow Set \leadsto T' \quad s\vdash e \Downarrow T' \leadsto e'}
  {s \vdash \mathsf{Ann}(e, T) \Uparrow T' \leadsto \mathsf{Ann}(e', T')}

  \\
  \textbf{Checked terms} \\
  \inferrule*[Right=Pi]
  {s \vdash A \Downarrow Set \leadsto A' \quad (x_{fresh}, A')::s \vdash B \Downarrow Set \leadsto B'}
  {s \vdash (x : A) \rightarrow B \Downarrow Set \leadsto (x_{fresh} : A') \rightarrow B'fresh}

  \inferrule*[Right=Lam]
  {(x_{fresh}, A)::s \vdash b \Downarrow B \leadsto b'}
  {s \vdash  \backslash x. b \Downarrow (x : A) \rightarrow B \leadsto \backslash x_{fresh}. b'}

  \inferrule*[Right=Unknown]
  {s \vdash e \Uparrow T' \leadsto e' \quad T' \equiv T}
  {s \vdash e \Downarrow T \leadsto e'}
\end{mathpar}

\subsection{Variables and substitution}\label{sec:substitution}

As outlined in \cref{sec:statix}, a dependently typed checker must track both a
typing context, which maps names to types, and substitutions, which map
names to values for beta reduction. A reference must resolve to the
closest enclosing declaration of the same name, which is exactly what lexical
resolution in a scope graph provides. We therefore represent the context as a
scope graph in which every binder creates a descendant scope that references its
parent via a $P$ edge. For example, the following program generates the
scope graph in \cref{fig:my_label}:


\begin{lstlisting}[caption={let introduces a scope}, label=listing:smalllet]
  let x = Set;
  x :: Set
\end{lstlisting}

\noindent When the checker infers the type of a variable it will add a \texttt{hasTy} relation to the scope graph. In Statix, later references of the variable should resolve to this entry using the \texttt{getTy} rule:

\begin{mathpar}
\inferrule*[Right=get-Ty]
{(x = id), P^* \vdash s \stackrel{hasTy}{\mapsto} (id, ty)  }{\mathsf{getTy}(s, x) = ty}
\end{mathpar}

\noindent Following the formalisation of scope graph queries in ``Scopes as
types'' \autocite{van_antwerpen_scopes_2018}, the query starts from scope $s$,
follows paths matching \(P^*\), and returns the type \(ty\) of the closest
\(\mathsf{hasTy}\) declaration whose identifier matches $x$. The same mechanism
accounts for shadowing, imports, and other name-resolution features.

\paragraph{Substitutions.} Besides the typing context, the checker must store
substitutions. Consider an extension of \cref{listing:smalllet} in which
\texttt{x} is used inside a type:

\begin{lstlisting}
  let x = Set;
  \a. a :: Set -> (\T. T) x
\end{lstlisting}

\noindent Checking this program requires type-level computation: applying
\texttt{\textbackslash T. T} to \texttt{x} and then substituting
\texttt{Set} for \texttt{x}. Substituting eagerly would force re-checking and
traversing whole terms, and would lose the link between errors and source
locations that Statix maintains. Normalisation by evaluation
\autocite{abel2007oneuniverse} relies on meta-level functions, which Statix's
first-order terms do not have. We therefore follow a call-by-name strategy
\autocite{plotkin1975call} and store substitutions explicitly in the scope graph,
as done in earlier Statix type checkers
\autocite{van_antwerpen_scopes_2018, none_dependently_2023}. A separate relation
\texttt{subst} pairs an \texttt{ID} with a \texttt{Closure(scope, Expr)}, an
expression together with the scope in which its free variables are declared:
\[ \mathsf{subst} : \mathsf{ID} \rightarrow \mathsf{Closure} \]
Closures may themselves contain variables with \texttt{subst} relations in other
scopes, so reduction evaluates them recursively through the primitive
$\mathsf{lookupSubst}$:
\[
\inferrule*[Right=lookup-Subst]
{(x = id), P^* \vdash s \stackrel{subst}{\mapsto} (id, Closure(s', t))}{\mathsf{lookupSubst}(s, x) = Closure(s', t)}
\]

A drawback of call-by-name is that a let-bound variable used several times is
evaluated at every use site.

\paragraph{Name capture.} In the substitution
$e[x := t]$, free variables of $t$ must not become bound in $e$. Naive
substitution gets the following example wrong, because the free $y$ is captured
by the binder $y$:
\[
  \texttt{(\textbackslash x.\textbackslash y.x) y} \betared \texttt{\textbackslash y.y}
\]
The usual solution is a nameless representation such as de Bruijn indices.
However, Statix connects names in the syntax to their declarations through
resolution paths, and these names are also the link to editor services such as
go-to-definition and error reporting. Translating bound variables to indices
would discard exactly the names that Statix is designed to reason about.

Instead, our implementation keeps names in the term language, but distinguishes
between two kinds of variable identifiers. User-written variables are
represented by their syntactic names \texttt{Loc(string)}. Internally generated variables are represented by a \texttt{Fresh(scope, string)} constructor, which associates the syntactic name with the scope in which it was declared. Thus, the implementation can preserve the source-level names needed by Statix while still avoiding accidental capture during substitution. Two syntactic variables with the same name will be converted to different fresh variables if and only if their declarations are different (are in different scopes).

Before a term is checked or inferred, the binders relevant to that term are
freshened. Freshening replaces a syntactic binder name by a fresh internal name,
and occurrences bound by that binder are made to refer to the fresh name. For
example, the term

\[
  \texttt{\textbackslash Loc(y). Loc(y)}
\]

\noindent will be internally represented as

\[
  \texttt{\textbackslash Fresh(s, y). Fresh(s, y)}
\]

\noindent where \texttt{Fresh(s, y)} is a fresh name generated for the binder. The printed name may still be \(\texttt{y}\), but the identity used by the type checker is unique.
Consequently, a substitution should never insert a term containing a free
syntactic variable \(\texttt{Loc(y)}\). \texttt{Loc} variables can be captured by binders. In order to resolve the declaration of a \texttt{Loc} variable, the scope graph queries \texttt{lookupSubst} and \texttt{getTy} match the name with the closest lexical match, which should be a \texttt{Fresh} variable already.
In the Statix code we account for this by adding another case for the two queries:
\begin{mathpar}
\inferrule*[Right=get-Ty-Loc]
{(x = \mathsf{toString}(id)), P^* \vdash s \stackrel{hasTy}{\mapsto} (id, ty)  }{\mathsf{getTy}(s, Loc(x)) = ty}
\\
\inferrule*[Right=lookup-Subst-Loc]
{(x = \mathsf{toString}(id)), P^* \vdash s \stackrel{subst}{\mapsto} (id, Closure(s', t))}{\mathsf{lookupSubst}(s, Loc(x)) = Closure(s', t)}
\end{mathpar}
Here \texttt{toString} obtains the original string name from \texttt{Loc} or \texttt{Fresh} constructors. With this representation, the earlier example is handled without relying on
de Bruijn indices:
\begin{align*}
  \texttt{(\textbackslash x.\textbackslash y.x) y}
  &\leadsto
  \texttt{(\textbackslash Fresh(s1, x).\textbackslash Fresh(s2, y).Fresh(s1, x)) Fresh(s3, y)} \\
  &\betared \texttt{\textbackslash Fresh(s2, y).Fresh(s3, y)}
\end{align*}
The binder \texttt{y} and the free variable \(\texttt{y}\) are converted to different identifiers, even though they may have the same surface spelling. Therefore, the free variable remains free after substitution.

\subsection{Beta reduction}
\label{sec:beta-reduction}

The checker needs two reduction routines. Weak head normalisation (whnf)
reduces only the head of a term. For instance, $(\lambda x.\ x)\ Set$ reduces to $Set$,
whereas $\lambda x.\ ((\lambda y.\ y)\ x)$ is already in weak head normal form.
Our Statix implementation performs head reduction with an explicit argument
spine of closures. Let-bindings and beta-redexes do not substitute into the
body. Instead, they extend the current scope with a delayed \texttt{subst}
binding for a fresh name, and variables are reduced only when
$\mathsf{lookupSubst}$ finds such a binding. Full normalisation first computes
the weak head normal form and then normalises the immediate subexpressions,
continuing under binders. Most typing rules only need to inspect the outermost
constructor of a type, so the checker uses whnf. Full normalisation is used to
display types and to compute the codomain of a Pi type after application, so
that \texttt{f 1 2} with
\texttt{f :: (x : Nat) -> (y : Nat) -> (Fin x, Fin y)} has type
\texttt{(Fin 1, Fin 2)} rather than a type with pending substitutions.
\Cref{app:reduction} gives the complete rules.

\subsection{Equality}
Following Martin-L{\"o}f type theory \autocite{martinlof1984intuitionistic},
equality is a type constructor rather than a boolean test. $x \equiv y$ is a
type for any $x, y$ of the same type, and its only canonical inhabitant is
$\mathsf{refl}$, which proves $x \equiv y$ exactly when $x$ and $y$ are
\emph{definitionally equal}, that is, equal up to reduction.

In our language the equality type is written
\texttt{==} (e.g.\ \texttt{Set == Set}), and checking it requires both sides to
have the same type. Reflexivity is built into the syntax as \texttt{refl}, a
checked term whose expected type must be $x == y$ with $x$ unifying with $y$.
Unlike in Martin-L{\"o}f's formulation, \texttt{refl} takes no arguments. This
loses no generality, because they can always be recovered from the expected
type:
\begin{mathpar}
  \inferrule*[Right=Eq]
  {s \vdash x \Uparrow A \leadsto x' \quad s \vdash y \Downarrow A \leadsto y'}
  {s \vdash x == y \Downarrow Set \leadsto x'==y'}
  
  \and

  \inferrule*[Right=Refl]{s \vdash x \equiv y}{s \vdash \mathsf{refl} \Downarrow x == y}
\end{mathpar}
For example, checking \texttt{(\textbackslash x. refl) :: (x : Set) -> (x == x)}
only requires unifying $x$ with itself, which holds trivially.

\subsection{Statements and forward references}

To make definitions convenient, programs consist of zero or more statements
optionally followed by a single expression:
\begin{lstlisting}[language=SDF3, caption=Syntax for statements]
Start.Program = [[Stmt*] [Expr]]
Start.ProgramOnly = [[Stmt*]]
  
Stmt.Def = [def [ID] : [Expr]; [ID] = [Expr];]
Stmt.Postulate = [postulate [ID]: [Expr];]
\end{lstlisting}
A postulate attaches a type to a name without a value, so beta reduction treats
the name as irreducible. A definition attaches both a type and a body.

\paragraph{Forward references with scope graphs.} Unlike the C language, where top-level
definitions may only refer to earlier ones, languages such as Java allow
\emph{forward references} between top-level definitions. Ad-hoc compilers
typically implement this with two passes: one that collects signatures and one
that checks bodies. With scope graphs no extra pass is needed. The Statix
solver delays a query until it is certain that its result cannot change, that
is, until no more bindings can be added to the scopes it searches. All
statements share a single top-level scope $S_{stmt}$ and are processed in
program order. Each checked signature adds a \texttt{!hasTy} binding to
$S_{stmt}$, and a query for a name that has not been declared yet is simply delayed.
Once Statix establishes that $S_{stmt}$ cannot be extended further, every delayed
query resolves, either successfully or with an error. Consider the following
program, where the body of \texttt{g} refers to \texttt{f}, \texttt{suc}, and
\texttt{zero} before they are declared:

\begin{lstlisting}[caption=Forward references between statements, label=listing:forward-references]
postulate Nat : Set;

def g : Nat;
g = f (suc zero);

def f : Nat -> Nat;
f = \n. suc n;

postulate suc : Nat -> Nat;
postulate zero : Nat;
\end{lstlisting}
The checker adds bindings for \texttt{Nat} and for the signature of \texttt{g}.
Checking the body of \texttt{g} then produces queries for the types of
\texttt{f}, \texttt{suc}, and \texttt{zero}, which the solver delays. As the
remaining statements add \(\texttt{hasTy}(f, Nat \to Nat)\),
\(\texttt{hasTy}(suc, Nat \to Nat)\), and \(\texttt{hasTy}(zero, Nat)\), the
delayed queries resume and \texttt{f (suc zero)} is checked against
\texttt{Nat}. Constraints are thus emitted in program order but resolved in
dependency order.

\paragraph{Mutual references.} The same mechanism supports mutually recursive
definitions, such as \texttt{g = \textbackslash n. f (suc n)} and
\texttt{f = \textbackslash n. g n}, as long as the cycle is only in the bodies.
The binding for each signature is added before its body is checked, so the body
of \texttt{g} waits only until the signature of \texttt{f} has been processed.
If the mutual dependency appears in the signatures themselves, neither binding
can be added before the other is resolved, and the current implementation
rejects the program.

\subsection{Modules}

Modules are a second source of non-lexical scoping in our language. We treat
them purely as name-resolution constructs, since a module is a named scope whose
declarations can be reached through qualified names such as \texttt{A.B.y} or
made available for unqualified lookup by opening the module. The language
supports module declarations, nesting, qualified access, and \texttt{open}
statements:

\begin{lstlisting}
module A {
  def x : Set;
  x = ...
  module B {
    def y : Set;
    y = ...
  }
}
module C {
  open A;
  def z : Set;
  z = x;
}
let w = A.B.y;
\end{lstlisting}

\noindent A nested module such as \texttt{B} can refer to the declarations of
its enclosing module through ordinary lexical lookup. Resolving \texttt{A.B.y}
resolves \texttt{A}, then \texttt{B} inside the scope of \texttt{A}, and finally
\texttt{y} inside the scope of \texttt{B}. Opening \texttt{A} in \texttt{C}
makes \texttt{x} visible in \texttt{C} although \texttt{A} is not a lexical
parent of \texttt{C}, which is the main source of non-lexical scoping.

Declaring and opening a module are statements:

\begin{lstlisting}[language=SDF3, caption=Syntax for module statements]
Stmt.Module = [module [ID] { [Stmt*] }]
Stmt.Open = [open [ID];]
\end{lstlisting} 
\paragraph{Module declaration.} Declaring a module creates a binding in the scope
in which it is defined, so that it can be referred to by name. The module's body
is checked in a child scope linked to the enclosing scope via a $P$ edge, and a
new relation \texttt{!modBind[ID, scope]} associates the module name with that
body scope. Because the body scope is a sibling of other scopes rather than a
parent, primitives such as \texttt{getTy} and \texttt{lookupSubst} never enter
a module accidentally.

\paragraph{Opening modules.} A new primitive
\texttt{getModule : (scope, ID) -> scope} resolves a module name by querying
\texttt{modBind} along paths $P^*$, preferring the lexically closest module.
Opening the module then adds an $I$ edge from the current scope to the module's
scope. Using a separate label for imports lets us distinguish names resolved
lexically from names resolved through an import. \Cref{fig:scopegrahimport}
shows the scope graph for the following program:
\begin{lstlisting}[caption={Opening a module}, label=lst:moduleresolution]
module B {
  postulate x : Set;
}
module A {
  open B;
  x
}
\end{lstlisting}

\paragraph{Name resolution.} With the new edge, \texttt{getTy} and
\texttt{lookupSubst} accept paths of the form $P^* I?$, so resolution may walk
at most one import. Local and imported declarations of the same name may then
conflict. Agda lets users hide names when opening a module, whereas OCaml prefers local
names over imported ones. We want to follow the OCaml convention, but Statix's prefix-based path ordering cannot express this. With the label
order $P < I$ it correctly prefers $PPP$ over $PPI$, but when a name is only
reachable through imports it would prefer $PPI$ over the closer import $PI$. We
therefore resolve names in two phases: first along $P^*$ only, and, if no
declaration is found, along $P^* I$, preferring the shortest path in both
phases.

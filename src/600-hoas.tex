\section{\label{sec:ScopeGraphs}A comparison of scope graphs and HOAS}

Our Statix implementation represents binding explicitly in scope graphs. This
suits constructs whose visibility does not follow the nesting of the abstract
syntax tree, such as modules, but it also means that substitution,
$\alpha$-renaming, and higher-order unification must be implemented over a
first-order representation of terms. To see how the implementation changes when
binders and metavariables are primitive, we implement the core of the same
language in Elpi, a dialect of $\lambda$Prolog designed for manipulating syntax
with binders and unification variables \autocite{dunchev_elpi_2015}. Elpi
supports higher-order abstract syntax (HOAS), in which object-language binders
are represented by meta-language binders \autocite{pfenning_higher-order_nodate},
so substitution and $\alpha$-renaming are delegated to the Elpi runtime.

We do not claim that either representation is universally preferable. HOAS is
convenient for the locally scoped binders of lambda abstractions and dependent
function types, whereas scope graphs give an explicit account of name
resolution that benefits modules, imports, qualified references, and other
forms of non-lexical scope.

\subsection{Logic programming in Elpi}

An Elpi program consists of relations defined by logical clauses, whose
predicate declarations may specify the input and output modes of their
arguments. The main judgments of our type checker are:

\begin{lstlisting}[language=Elpi, caption={The principal relations of the Elpi type checker},
label={lst:elpi-judgements}]
pred infer i:tm, o:tm, o:tm.
pred check i:tm, i:tm, o:tm.
pred whnf i:tm, o:tm.
pred conv i:tm, i:tm.
\end{lstlisting}

As in Statix, \lstinline|infer T T' A| states that the source term
\lstinline|T| elaborates to \lstinline|T'| and synthesises type \lstinline|A|,
and \lstinline|check T A T'| checks \lstinline|T| against \lstinline|A| and
elaborates it to \lstinline|T'|. Separating source from elaborated terms allows
occurrences of \lstinline|hole| to be replaced by Elpi unification variables.
Clause variables are implicitly universally quantified. During proof search,
Elpi selects a clause whose conclusion unifies with the goal and proves its
premises, so unification serves both to match inputs and to construct outputs.

\paragraph{Generic and existential variables.}
Elpi distinguishes eigenvariables, introduced by \lstinline|pi x\ Goal|, from
unification variables, introduced by \lstinline|sigma M\ Goal|. The
\lstinline|pi| quantifier introduces a fresh rigid constant that cannot be
unified with an arbitrary term, which makes it suitable for representing an
object-language variable while traversing a binder. The position of the
quantifiers determines which variables a solution may mention:
\lstinline|pi x\ sigma M\ M = x| succeeds because \lstinline|M| is introduced
while \lstinline|x| is in scope, whereas \lstinline|sigma M\ pi x\ M = x| fails
because \lstinline|M| may not capture a variable introduced after it. An outer
metavariable may still depend on a later binder when it is applied to it: in
\lstinline|sigma M\ pi x\ M x = x|, Elpi solves \lstinline|M| with
\lstinline|x\ x|. This is exactly the representation of metavariables from
\cref{sec:hou}. A hole below the binders \lstinline|A| and \lstinline|x| becomes
\lstinline|M A x|, whose solution may depend on either binder but not on any
variable that was out of scope when the metavariable was created.

\paragraph{Hypothetical clauses.}
The typing context is represented by hypothetical clauses rather than an
explicit list. The fact \lstinline|localTy X A| records that \lstinline|X| has
type \lstinline|A|, and a variable is typed by the clause
\lstinline|infer X X A :- localTy X A|. Below a binder, the checker extends the
program temporarily with \lstinline|pi x\ localTy x A ==> Goal|: the fact is
available while \lstinline|Goal| is solved and is removed afterwards. Together,
\lstinline|pi| and \lstinline|==>| therefore correspond directly to extending the
context to $\Gamma, x : A$. Because the runtime manages this context along the
lexical structure of the computation, no context parameter has to be threaded
through the typing rules.

\subsection{Defining the language in HOAS}

\Cref{lst:elpi-syntax} gives the Elpi representation of the core language.

\begin{lstlisting}[language=Elpi, caption={The syntax of the language in Elpi},
label={lst:elpi-syntax}]
kind tm type.
type set  tm.
type eq   tm -> tm -> tm.
type refl tm -> tm.
type app  tm -> tm -> tm.
type lam  (tm -> tm) -> tm.
type arr  tm -> (tm -> tm) -> tm.
type ann  tm -> tm -> tm.
type hole tm.
\end{lstlisting}

The constructor \lstinline|set| is the universe of types, for which we use the
simplified rule \lstinline|set : set|. Only \lstinline|lam| and \lstinline|arr|
contain meta-level functions: $\lambda x.t$ is represented as
\lstinline|lam (x\ T)| and $(x : A) \to B$ as \lstinline|arr A (x\ B)|. There is
no constructor for bound variables. Occurrences of \lstinline|x| are Elpi
variables bound by the meta-level abstraction, so object-level
$\alpha$-equivalence is meta-level $\alpha$-equivalence. The remaining
constructors are first-order: \lstinline|ann T A| annotates a term with a type,
\lstinline|eq L R| is the equality type, \lstinline|refl| is checked against an
equality whose sides are definitionally equal, and \lstinline|hole| is a
placeholder that is elaborated to a unification variable. The polymorphic
identity function $\lambda A.\lambda x.x :: (A : \mathsf{Set}) \to (x : A) \to A$
is written as follows:

\begin{lstlisting}[language=Elpi, caption={The polymorphic identity function in HOAS},
label={lst:elpi-identity}]
ann (lam (A\ lam (x\ x))) (arr set (A\ arr A (x\ A)))
\end{lstlisting}

\subsubsection{Bidirectional type checking}

Lambda abstractions and reflexivity are checked against an expected type,
whereas applications and annotated terms are inferred.
\Cref{lst:elpi-rules} shows the rules for dependent function types, lambda
abstractions, and application.

\begin{lstlisting}[language=Elpi, caption={Typing rules for binders and application},
label={lst:elpi-rules}]
infer (arr A B) (arr A1 B1) set :-
  check A set A1,
  pi x\ localTy x A1 ==> check (B x) set (B1 x).

check (lam F) Expected (lam G) :-
  whnf Expected (arr A B),
  pi x\ localTy x A ==> check (F x) (B x) (G x).

infer (app F X) (app F1 X1) Result :-
  infer F F1 FunctionType,
  whnf FunctionType (arr A B),
  check X A X1,
  Result = B X1.
\end{lstlisting}

Applying the meta-level function \lstinline|B| to the fresh eigenvariable
\lstinline|x| opens the object-language binder, and because \lstinline|x| is
passed explicitly to \lstinline|B1|, the elaborated codomain may depend on it.
The lambda rule follows the declarative rule closely: the expected type is
reduced to a function type, \lstinline|x| is assigned the domain \lstinline|A|
by a hypothetical clause, and the body \lstinline|F x| is checked against
\lstinline|B x|. No freshness side condition is needed, since the eigenvariable
is fresh by construction and scoped to the recursive call. In the application
rule, \lstinline|Result = B X1| substitutes the argument into the codomain by
meta-level application, where the scope graph implementation needs an explicit
substitution operation.

\subsubsection{Substitution and normalisation}

The advantage of HOAS is clearest in $\beta$-reduction. Since \lstinline|app|
admits $\beta$-redexes, we still need weak head normalisation:

\begin{lstlisting}[language=Elpi, caption={Beta reduction through meta-level application},
label={lst:elpi-beta}]
whnf (app F X) R :-
  whnf F F1,
  whnf-app F1 X R.
whnf T T.

whnf-app (lam Body) X R :-
  whnf (Body X) R.
whnf-app F X (app F X).
\end{lstlisting}

\noindent In \texttt{whnf-app}, \lstinline|Body X| substitutes \lstinline|X|
for the variable bound by \lstinline|Body|. The runtime performs this through
meta-level $\beta$-reduction, which is capture-avoiding without an explicit
traversal or freshening of the object-language term. For example,
\lstinline|app (lam (x\ x)) set| reduces via \lstinline|(x\ x) set| to
\lstinline|set|. Scope graphs, in contrast, keep binders and references as
first-order syntax. They determine which declaration an occurrence denotes, but
do not perform substitution, so our Statix implementation must define it
explicitly, preserve the binding relationships of the substituted term, and
avoid capture when a term moves below a binder (\cref{sec:substitution}).

The same machinery gives reflexivity its meaning. Equality \lstinline|eq L R|
infers the type of \lstinline|L| and checks \lstinline|R| against it, and
\lstinline|refl T| has the inferred type \lstinline|eq T1 T1|. Unifying this
type with an expected equality forces both sides to unify with the same term,
possibly after normalisation, so \lstinline|refl| succeeds whenever the two
sides are definitionally equal. For instance, \lstinline|refl x| checks against
$(\lambda y.y)\;x \equiv x$ because conversion reduces the left-hand side to
\lstinline|x|.

\subsubsection{Holes and scoped metavariables}

A \lstinline|hole| is elaborated to an Elpi unification variable that records
the eigenvariables in scope where it occurs. Checking
\lstinline|lam (A\ lam (x\ hole))| against
\lstinline|arr set (A\ arr A (x\ A))| elaborates the hole to a metavariable that
occurs as \lstinline|M A x|. Its solution may be \lstinline|x|, a term depending
only on \lstinline|A|, or a closed term, provided it has the expected type.
Elpi exposes this context through built-ins: \lstinline|names L| returns the
eigenvariables in scope, and \lstinline|prune V L| unifies \lstinline|V| with a
unification variable that sees only the names in \lstinline|L|. With these two
primitives, object-language holes become Elpi metavariables directly. Elpi's
higher-order unification then performs the pattern checks and delays
constraints outside the pattern fragment, all of which our Statix
implementation has to provide itself (\cref{sec:Inference}).

\subsection{HOAS as an alternative to scope graphs}

The HOAS implementation delegates much of the work of manipulating binders to
the meta-language, but the context managed by \lstinline|pi| and hypothetical
clauses is lexical and stack-structured: a hypothetical declaration exists only
while its subgoal is being solved. This matches lambda abstractions and
dependent function types, where a variable is visible only in the body. Module
systems, however, create visibility between parts of the program that are not
related in the syntax tree. In \cref{lst:moduleresolution}, the declaration of
\lstinline|x| in module \lstinline|B| is not a lexical ancestor of its use in
\lstinline|A|. In the scope graph (\cref{fig:scopegrahimport}), resolving
\lstinline|x| follows the import edge from $s_A$ to $s_B$, and that edge serves
every reference in \lstinline|A|. A purely HOAS implementation cannot obtain
this by opening an object-language binder, because the declaration and its use
lie in different branches of the tree and visibility is created by the
\lstinline|open| statement rather than by nesting. The implementation must
instead locate the module, retrieve its exported declarations, and make them
available while checking the rest of the body, with additional policies for
shadowing and qualified access. Such an encoding is possible in Elpi, for
example through an explicit environment or relations describing modules and
their exports, but it gives up the simplicity of the hypothetical context: name
resolution becomes a separate user-defined mechanism layered on top of HOAS.
